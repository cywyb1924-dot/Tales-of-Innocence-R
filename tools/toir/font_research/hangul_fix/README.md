# FontDataNormal.pgf 한글 charmap 버그 수정 (2026-08-09)

## 배경

이전 세션에서 `_Data/Font/FontDataNormal.pgf`(게임 자체 내장 PGF 폰트 파일)에
한글 글리프를 수동으로 주입했는데, 그 작업을 한 스크립트가 이 저장소에 남아있지
않았다(`font_research/README.md` 참고 — 결과물만 존재, 재현 불가).

이번 세션에서 보고된 두 버그를 조사하다가, 그 잃어버린 주입 작업 자체에 있던
버그를 발견해서 고쳤다:

> "스킵"이 "스었"으로 보이는 등, 특정 한글 낱자가 완전히 다른 낱자로 바뀌어
> 보이는 문제.

## 근본 원인

PGF 포맷은 `charmap[문자코드 - firstGlyph]` → glyph 인덱스로 찾아가는 테이블을
쓴다(PPSSPP `Core/Font/PGF.cpp`의 `PGF::ReadPtr`/`GetCharGlyph` 참고, 이 폴더의
`pgf_parse.py`가 그 로직을 파이썬으로 그대로 포팅한 것).

원래 한글 글리프가 없던 이 폰트는 새 glyph 1107개를 추가하면서
`charPointerLength`(전체 glyph 개수)가 7515 → 8622로 늘었다. 문제는, "이 문자는
글리프가 없다"는 걸 표시하려고 charmap에 박아넣은 값이 `8191`(=13비트 필드의
전체-1, 옛 `charMapBpe=13`의 흔적)이었는데, glyph 개수가 8622개로 늘면서
**8191이 우연히 "유효한" glyph 인덱스가 되어버렸다.** (glyph #8191 자리에는
실제로 "었"의 글리프가 들어있었다.)

그 결과, 실제로 명시적으로 주입되지 않은 수만 개의 코드가 전부 glyph #8191
("었")을 가리키게 됐다. 번역 텍스트에서 실제로 쓰이는 한글 1336자 중 230자가
여기 걸렸다(코드는 각각 다르지만 전부 "었" 글리프로 렌더링됨). "었" 자신도
이 목록에 있었다 — 우연히 같은 슬롯을 썼을 뿐, "었"도 다른 문자들과 함께
충돌군에 속해 있었다.

## 조사·수정 스크립트

- **`pgf_parse.py`**: PGF 리더(헤더/charmap/glyph 테이블/glyph 메트릭 파싱).
  PPSSPP 소스에서 직접 포팅, 바이트 단위로 100% 검증됨.
- **`scan_hangul_usage.py`**: `2_translated/**/*.csv`의 `Korean` 컬럼을 전수
  스캔해서 실제로 게임에 쓰이는 한글 음절 집합(1336자)을 뽑아냄.
- **`build_fix.py`**: 실제 수정을 수행.
  1. 실사용 1336자 중 8191 충돌에 걸린 230자를 찾음(이미 정상인 "었" 1자는
     제외, 나머지 229자).
  2. 229자를 `C:\Windows\Fonts\malgun.ttf`(맑은 고딕)로 새로 래스터라이즈해서
     PGF 형식의 새 glyph 레코드(4bpp nibble RLE 압축, PPSSPP
     `PGF::DrawCharacter` 디코더의 역연산)를 만들어 `fontData`에 추가.
  3. 이 229자의 charmap 엔트리를 새 glyph 인덱스로 재작성.
  4. 8191을 가리키던 나머지(실사용 안 하는) 56,658개 charmap 엔트리를
     명시적 invalid 값(16383)으로 재작성 — 더 이상 엉뚱한 글자를 보여주지
     않고 "글리프 없음"으로 정상 처리되게 함.
  5. **부수적으로 발견한 2차 버그**: 새 glyph들이 추가되며 `fontData`
     블롭이 커졌는데, glyph 위치를 가리키는 `charPointerTable`의 필드 폭
     (`charPointerBpe=19비트`, 워드 오프셋 최대 524287)을 초과하는 시점부터
     오프셋 값이 잘려서(overflow) 이후 glyph들이 전부 깨져 보였다(가로/세로가
     수십~백 단위로 터무니없이 큰 값). `charPointerBpe`를 21비트로 늘려서 해결.
     **8191 버그와 정확히 같은 종류의 실수**(데이터가 커질 걸 예상 못 하고
     비트 폭을 고정값으로 잡아서 나중에 조용히 오버플로우)였다는 점이 흥미롭다.

## 검증

- 실사용 1336자 전부 재파싱해서 glyph 데이터 존재 확인, 충돌 0건 확인.
- 새로 추가한 229개 glyph 전부 왕복 검증(내가 쓴 메트릭 == 다시 읽은 메트릭)
  통과.
- 8개 표본 문자(킵/훔/괭/풋/좁/핏/스/갹)를 실제로 픽셀까지 디코드해서 PNG로
  렌더링, 육안으로 정상적인 한글 모양임을 확인.
- Windows Vita3K 실기 부팅으로 원래 버그("물공" 스탯 숫자 겹침)가 이 폰트
  파일과 무관함을 확인(숫자 글리프 자체는 원본과 바이트 단위로 동일 — 별도
  이슈로 분리, 아래 참고).

## 🔴 실기 테스트에서 발견한 크래시 — 결국 이 세션에서는 완전한 수정을 포기함

정적 검증(위 항목들)은 전부 통과했지만, 실제로 Windows Vita3K에 넣고 부팅해보니
오프닝 동영상(`_Data/Movie/movie_002.mp4`) 재생 중 100% 재현되는 크래시가
발견됐다:

```
sceClibMemcpy(dst, src, 4294967288) src/dst overlap  (크기가 -8을 부호없는 정수로
잘못 해석한 값 — 어딘가에서 크기 계산이 음수가 됨)
→ EXCEPTION_ACCESS_VIOLATION
```

**Vita3K는 PGF를 재구현한 게 아니라 실제 PS Vita 펌웨어의 `libpgf` 모듈을
그대로 LLE로 돌린다** (PPSSPP처럼 C++ 재구현이 아님). 그래서 이 프로젝트가
참고한 PPSSPP `Core/Font/PGF.cpp`(이 폴더 `pgf_parse.py`가 포팅한 그 로직)를
정확히 만족해도, 실제 Sony 펌웨어 코드가 기대하는 더 엄격한/다른 규칙을
어겼을 가능성이 있다 — 그리고 소스가 없는 클로즈드 펌웨어라 정확한 규칙을
알아낼 방법이 없다.

### 원인 분리 실험 (전부 실기 부팅으로 직접 확인)

| 실험 | 내용 | 결과 |
|---|---|---|
| bpe만 확장 | glyph 데이터/charmap은 옛날(버그) 상태 그대로, `charPointerBpe`만 19→21로 확장 | **크래시 없음** |
| orphan | 229개 glyph 데이터는 전부 추가(파일 크기/테이블 그대로 키움)하되 charmap은 아무것도 안 바꿔서 새 glyph를 아무도 안 가리킴 | **크래시 없음** |
| 문자 1개 | "훔" 딱 1자만 실제로 새 glyph 만들어서 매핑 | **크래시 없음** |
| 문자 2개 | "링","콜" 2자만 매핑 | **크래시 없음** (3분+ 이후까지 정상) |
| 문자 10개 | 상위 10자 매핑 | **크래시 재현** (약 2분22초 후) |
| 문자 115개 | 상위 115자 매핑 | **크래시 재현** (약 2분23초 후) |
| 문자 229개(전체) | 전부 매핑 | **크래시 재현** (약 5~6초 후, 훨씬 빠름) |

즉:
- 테이블 크기·비트폭 확장 자체는 무관 (bpe/orphan 실험이 증명).
- 특정 글자 하나의 데이터 문제도 아님 ("훔" 단독은 안전했는데 다른 9자와
  같이 있으면 크래시).
- **크래시까지 걸리는 시간이 실험마다 들쭉날쭉하고(2~3분 vs 5~6초), 새로
  매핑한 glyph 개수가 많을수록 더 빨리/더 확실하게 재현된다** — 결정론적
  버그(특정 바이트 패턴)라기보다, 새 glyph를 참조하는 폰트 렌더링 호출이
  누적될수록 확률적으로 터지는 **레이스 컨디션/메모리 관리 버그**로 보인다.
  이 프로젝트가 만든 PGF 파일 내용의 문제라기보다 Vita3K(이 LLE 경로) 자체의
  불안정성일 가능성이 높다.

### 이번 세션이 실제로 배포한 것: `build_fix_safe.py`

새 glyph를 아예 추가하지 않는(그래서 위 크래시를 원천 차단하는) 최소 수정.
`FontDataNormal.pgf`의 charPointerLength/Bpe/glyph 데이터는 전혀 안 건드리고,
charmap 값만 고친다:

- 8191(버그 sentinel)을 가리키던 항목 중, 진짜 그 glyph의 주인인 "었"
  1자만 그대로 두고, 나머지(실사용 229자 + 미사용 수만 개)는 전부 명시적
  invalid 값(16383)으로 재작성.
- 결과: "스킵"이 "스었"처럼 **엉뚱한 글자로 잘못 보이는 문제는 사라짐**
  (대신 빈칸/대시로 표시됨). 크래시 없음(실기로 직접 확인, movie_002.mp4
  통과 + 이후 대사까지 정상).
- **229자 자체가 올바른 모양으로 나오게 하는 건 이번 세션에서는 못
  끝냈다.** 다음 세션에서 이어가려면 위 표의 실험을 참고해서 "왜 2개는
  되고 10개는 안 되는지"부터 다시 파고들어야 한다(더 최신 Vita3K 빌드로
  같은 실험을 재현해보는 것도 방법 — 이번 세션은 `VITA3K_NEW`
  v0.2.0 3625-839e8d39 빌드 하나로만 테스트함).

## 관련이 없는 것으로 확정된 별개 버그

- **숫자 겹침/오출력** ("물공 6701"이 두 자리가 겹쳐 보임): `FontDataNormal.pgf`의
  일반 숫자(0-9)·전각 숫자(０-９) 글리프는 원본과 완전히 동일함을 확인했다.
  실기로 재현해보니 HP/TP/NEXT 등 다른 숫자 표시는 전부 정상이고, 물공/물방/
  술공처럼 **4자리 숫자를 쓰는 특정 스탯 UI 위젯에서만** 두 자리가 같은 위치에
  겹쳐 그려진다 — 폰트 글리프 선택 문제가 아니라 그 UI 위젯의 자릿수 처리
  로직(게임 자체 코드) 쪽 문제로 추정된다. 이번 세션에서는 근본 원인을 특정하지
  못했다(ASM 리버싱이 추가로 필요, 다음 세션 과제).
- **오프닝 동영상(`_Data/Movie/movie_002.mp4`) 재생 시 크래시**: 처음엔
  "이 동영상 파일은 안 건드렸으니 순수 에뮬레이터 버그"라고 결론 내렸었는데,
  **틀렸다** — 나중에 직접 대조 실험으로 확인해보니 `build_fix.py`가 만든
  새 glyph 데이터가 있을 때만 재현되고, 옛날(버그 있는) 폰트로 되돌리면
  크래시 없이 잘 재생된다. 즉 이 크래시는 번역 패치와 **무관하지 않다** —
  바로 위 "실기 테스트에서 발견한 크래시" 항목이 최종 결론이다.

## 재현/재실행

```
python scan_hangul_usage.py   # hangul_usage_chars.tsv 생성 (경로는 스크립트 상단 상수 참고)
python build_fix.py           # FontDataNormal.pgf.fixed 생성 — 크래시 있음, 배포 안 함 (위 참고)
python build_fix_safe.py      # FontDataNormal.pgf.safefix 생성 — 실제 배포된 안전 버전
```

세 스크립트 모두 원래 이번 세션의 임시 작업 디렉토리 경로가 하드코딩되어 있다
(재실행하려면 상단 경로 상수를 현재 환경에 맞게 바꿔야 함). `build_fix_safe.py`는
`build_fix.py`가 만든 `categorize_out.txt`(어떤 문자가 8191 버그에 걸렸는지 목록)를
그대로 읽어 쓰므로, `build_fix.py`를 먼저 한 번 실행해서 그 파일을 생성해둬야 한다
(glyph를 실제로 추가하는 부분은 무시되고 목록만 재사용됨).
