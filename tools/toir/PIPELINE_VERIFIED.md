# 파이프라인 검증 결과 (2026-07-31)

`toidata_release.l7c` 안의 아이템 텍스트 1개를 한글로 바꿔서, 추출부터 패치 생성까지
전체 파이프라인을 실제로 돌려본 기록입니다.

## 검증한 것

1. **`extract.py`** → `1_extracted/ItemDataPack.csv`에서 일본어 원문 추출
2. **`Korean` 컬럼을 채운 CSV**로 `toir.formats.dat.items.recompile_items()` 호출
   → 새 `ItemDataPack.dat` 생성 (원본과 정확히 같은 크기, 고정 레코드 포맷이라 당연함)
3. **`l7ca_patch.py`**로 원본 `toidata_release.l7c`(1.4GB)에 이 파일 하나만 제자리 패치
4. 패치된 l7c를 `psvita-l7ctool`로 다시 통째로 압축 해제 (14,076개 파일 전부)해서
   - 우리가 바꾼 텍스트("사과 젤리" 등)가 정확히 보존되어 있는지
   - 다른 파일들이 깨지지 않았는지
   둘 다 확인
5. **`xdelta3`**로 원본 대비 diff 패치(71KB) 생성 → 그 패치를 원본에 적용한 결과가
   패치된 파일과 **바이트 단위로 완전히 동일**함을 `cmp`로 확인

## `l7ca_patch.py`가 하는 일과 이유

`psvita-l7ctool`의 `c`(전체 재생성) 명령은 **압축을 전혀 하지 않고** 저장하기 때문에,
원본이 1.4GB(실제로는 압축되어 있음)인데 반해 재생성 결과물이 2.2GB로 부풀어 오르고,
그 결과 아카이브 크기가 int32 범위(2^31-1 bytes ≈ 2GB)를 넘어서면서 `PackArchive`
내부의 `(int)` 캐스팅이 오버플로우해 헤더가 깨지는 걸 실제로 겪었습니다
(`toidata_release_test.l7c`를 다시 열면 `System.IO.IOException` 발생).

그래서 전체 재생성 대신, **바뀐 파일 하나만 원본 아카이브 끝에 비압축 상태로 추가**하고,
- 해당 파일의 `file_entry.offset`/`compressed_size`/`crc32`만 갱신
- 기존 청크 테이블 슬롯(4개)을 재사용 — 첫 슬롯에 전체 비압축 데이터, 나머지는 길이 0
- **다른 모든 파일의 위치·오프셋은 전혀 건드리지 않음**

이렇게 하면 아카이브가 딱 바뀐 파일 크기만큼만 커지고(이번 경우 +248KB), 압축을
재현할 필요도 없습니다. 단, 새 데이터 크기가 원본 `raw_size`와 다르면 이 방식은
쓸 수 없습니다 (스크립트가 자동으로 에러를 내고 중단합니다) — 그런 경우는 별도 전략이
필요합니다 (예: Script/Skit처럼 가변 길이 텍스트는 게임이 raw_size를 어떻게 쓰는지
먼저 확인 필요).

### 문자열 테이블 위치 버그 (직접 겪은 것)

`psvita-l7ctool`은 문자열 테이블 시작 위치를 `파일 전체 길이 - stringTableSize`로
**역산**합니다. 그래서 처음엔 그냥 새 데이터를 파일 맨 끝(EOF)에 이어붙였더니, 파일
길이가 늘어나면서 이 역산이 깨져 문자열 테이블을 엉뚱한 위치에서 읽어 UTF-8 디코딩
에러로 크래시했습니다. 고쳐서, 문자열 테이블을 먼저 메모리로 읽어둔 뒤 "원래 문자열
테이블이 있던 자리"부터 새 데이터를 쓰고 그 뒤에 문자열 테이블을 다시 붙이는 방식으로
바꿔서 해결했습니다 (다른 모든 절대 오프셋 테이블은 전혀 영향 없음).

## CRC32 불일치 경고에 대해

압축 해제 시 "Invalid CRC32" 경고가 35건 나오는데, **원본(수정 안 한) l7c를 그대로
압축 해제했을 때도 정확히 동일한 35건**이 나옵니다 (diff로 완전 일치 확인). 즉 이건
`psvita-l7ctool`의 압축 재구현(TaikoCompression2 계열로 추정) 자체의 기존 한계이지,
우리 패치와는 무관합니다. 우리가 수정한 `ItemDataPack.dat`은 원본·패치본 모두에서
CRC 문제 없이 정상입니다.

## 아직 검증 못 한 것 (이 환경의 한계)

- **실제 게임이 이 패치된 l7c를 로드하는지는 확인 못 했습니다.** 이 환경엔 PS Vita도
  Vita3K 에뮬레이터도 없어서, "파일 포맷 레벨에서 올바르다"까지만 확인했지 "게임
  런타임이 이걸 받아들이는지"는 미검증입니다. 특히 게임이 `raw_size`/`compressed_size`
  필드를 우리가 가정한 대로만 쓰는지, 아니면 뭔가 사전 할당 버퍼 크기 등으로 다르게
  쓰는지는 실기 테스트 전까지 100% 확신할 수 없습니다.
- 언어 코드 패치(`tools/asm/InnocenceR.asm`의 KOREAN 패치)도 마찬가지로 미검증입니다.
- Script.csv/Skit.csv처럼 **가변 길이** 텍스트에 대해서는 아직 이 파이프라인을
  시험해보지 않았습니다 (이번 검증은 고정 레코드 크기인 아이템 텍스트로만 진행).

## 재현 방법

```
python tools/toir/extract.py <소스> 1_extracted
# 1_extracted/ItemDataPack.csv에 Korean 컬럼 추가해서 2_translated/ItemDataPack.csv로 저장

```

## 2차 검증 (2026-08-02): Script.csv — 가변 길이 텍스트, 530개 파일 동시 패치

위 검증은 **고정 레코드 크기** 파일 1개로만 진행됐고, "아직 검증 못 한 것"
항목에 Script/Skit 같은 가변 길이 텍스트는 명시적으로 남겨뒀었습니다.
Script.csv(530개 씬, 8,162행) 전체 번역이 완료된 뒤, 이 gap을 실제로
메웠습니다.

### 1단계: 재컴파일(디코드→치환→인코드) 자체의 정확성

`toir.formats.script.script.Script.decompile()` / `.replace_texts()` /
`.recompile()`을 Story.csv의 530개 파일 전체에 대해 직접 호출하고, 재컴파일된
바이트를 **다시 디코드**해서 예외 없이 파싱되는지 확인(왕복 무결성 검사):

- **530/530 성공, 실패 0건**
- 525/530개 파일에서 크기가 원본과 달라짐(당연함 — 가변 길이 바이트코드
  포맷이라 한국어 인코딩 길이가 일본어와 다름). 전체 합계로는 오히려
  **원본보다 작아짐**(1,092,852 → 882,169바이트, -210,683바이트) — 아카이브
  용량 증가 우려는 기우였음.

### 2단계: `l7ca_patch.py`의 한계 발견 — 크기가 다르면 거부함

기존 `l7ca_patch.py`는 `len(new_data) != info['raw_size']`면 명시적으로
예외를 던지도록 설계돼 있음(안전장치). Script.csv 530개 중 525개가 이
케이스라 그대로는 못 씀 → **`l7ca_patch_multi.py`를 새로 작성**해서 여러
파일을 한 번에, 크기가 달라도 패치할 수 있게 확장함.

**포맷 이해를 위해 `taikotools/psvita-l7ctool/psvita-l7ctool/Program.cs`를
직접 재검토**해서 다음을 확인/정정함:
- 디스크 순서는 `헤더 → [파일 데이터 블롭] → 파일시스템 엔트리 →
  파일 엔트리 → 청크 테이블 → 문자열 테이블`이며, `metadata_offset`은
  파일 데이터 블롭 바로 다음(파일시스템 엔트리 테이블 시작)을 가리킴 —
  처음엔 "파일 앞쪽 근처"로 잘못 추측했었으나, 기존 단일 파일 패치가
  새 데이터를 삽입하는 위치(예전 문자열 테이블 시작 지점 = 청크 테이블
  끝 = 메타데이터 영역 전체가 끝나는 지점)가 이 metadata_offset보다
  **뒤**이기 때문에 실제로는 전혀 영향이 없었던 것으로 확인됨(다행히
  기존 코드가 우연히 안전한 위치를 골랐던 것).
- 청크 엔트리의 두 uint16 필드(`unk`, `chunkId`)는 읽기 경로에서 전혀
  쓰이지 않는 설명용 값(0으로 둬도 무방).
- `archive_size` 헤더 필드는 이 리더의 읽기 경로에서 전혀 참조되지 않음
  (정보성 필드) — 그래도 정확한 값으로 갱신하도록 구현.
- 문자열/폴더명은 여러 파일이 문자열 테이블 오프셋을 공유할 수 있으나,
  파일 엔트리는 filesystem-entry id와 1:1 대응이라 여러 파일을 독립적으로
  패치해도 서로 간섭 없음.

새 `l7ca_patch_multi.py`는 이 확인된 사실을 바탕으로, N개 파일의 새
데이터를 예전 문자열 테이블 위치부터 순서대로 이어 쓰고 문자열 테이블을
그 뒤에 재부착하는 방식으로 구현함 (기존 단일 파일 기법의 자연스러운
확장).

### 3단계: 실제 패치 + 전체 재추출 검증

`toidata_release.l7c`(1,475,397,012바이트)에 530개 파일을 한 번에 패치 →
`new_filesize=1,476,279,181`(+882,169바이트, 정확히 재컴파일된 데이터 총량과
일치) → `psvita-l7ctool`로 전체(14,076개 파일) 재추출해서 세 가지를 바이트
단위로 확인:

1. **패치한 530개 파일**: 재추출된 내용이 우리가 재컴파일해서 넣은 내용과
   SHA256 완전 일치 (530/530, 불일치 0건)
2. **패치하지 않은 나머지 436개 Script 파일 + 다른 모든 카테고리**: 원본과
   SHA256 완전 일치 (436/436, 불일치 0건 — 다른 파일에 전혀 영향 없음)
3. **CRC32 불일치 경고**: 원본을 그대로 추출했을 때와 정확히 동일한
   35건(diff로 완전 일치 확인) — 새로 발생한 손상 없음

### 4단계: xdelta 배포 패치 생성 및 재검증

`xdelta3`로 원본 대비 diff 패치(371,853바이트 ≈ 364KB) 생성 → 그 패치를
원본에 적용한 결과가 패치된 아카이브와 `cmp`로 바이트 단위 완전 동일함을
확인. 새로 정리한 `l7ca_patch_multi.py`(CLI 인터페이스로 재작성한 최종본)를
다시 처음부터 실행한 결과도 이전 결과와 완전히 동일함을 재확인(결정론적
동작 확인).

**결론**: Script.csv(가변 길이 텍스트) 전체가 실제 게임 아카이브 포맷
레벨에서 안전하게 패치 가능함을 확인했습니다. 남은 미검증 영역은 여전히
"실제 게임/에뮬레이터가 이 패치된 아카이브를 로드해서 정상 동작하는지"
뿐입니다(이 환경은 Vita3K 실행 불가).

재현 방법:
```
python tools/toir/l7ca_patch_multi.py <원본 toidata_release.l7c> <출력.l7c> 3_patched
xdelta3 -e -f -s <원본.l7c> <출력.l7c> script_translation.xdelta
```
